## 真实聊天调用链

1. `Core.ingest` 接收经过认证、去重的私聊事件，维护回复修订及后台工作；
   `AffectEngine.observe` 只从明确反馈记录短期交互状态。
2. 独立 worker 的 `Core.run_once` 先处理明确命令，再调用 `recall_for_reply` 和
   `Core.context`。记忆检索、相关性核对与正式回复是不同模型用途。
3. `Core.context` 组合 `PRINCIPLES`、Expression 指导、运行能力、分段规则、
   内容引用、Affect、经来源核验的记忆及表达学习、历史和当前输入。
   `dialogue_history` 保留真实 user/assistant 角色和已送达片段；来源与擦除状态会复核。
4. `fit_context` 先移除可选参考，再移除最旧的完整轮次，保留规则与当前输入。
   加长系统指导可能挤掉历史，因此本实验先冻结原版上下文，再仅改变系统指导。
5. `budget.reserve` → `budget.complete` → `ModelClient` 执行真实请求准入与结算。
   最终回复仍须通过来源、隐私 epoch、租约和回复修订检查。
6. Expression 解析表情意图；`split_text` 在原文上无损分段；Outbox 按幂等、送达
   回执与不确定状态交付。多条气泡可以来自同一次模型生成，并不证明主动发起多轮交流。

## 证据与假设

| 观察 | 类型与证据 | 可以下的结论 | 尚不能下的结论 |
|---|---|---|---|
| 普通输入可能被解释成任务 | `Core.context` 仍把部分空文本 rich/content 输入补成“请看看我分享的内容。”；#99 只覆盖无 rich/content 的空消息 | 有具体的输入意图改写，媒体主线负责修复 | 不是所有普通文本都被代码改成求助 |
| 长篇、完整的回应倾向 | `ExpressionEngine.instruction` 含“必须有完整文字回复”或“每次必须有完整文字回复”；仅在 expression 启用时出现 | 存在可能影响长度的指导 | “完整”不等于模型一定会输出长篇，因果须实验 |
| 每轮追问、关系分析 | `PRINCIPLES` 要求自然聊天与真实克制，没有要求每轮提问、每轮建议或身份分析 | 不能将这些现象归因于不存在的硬编码问句模板 | 基础模型习惯、Prompt 组合与上下文影响尚未分离 |
| 缺少自己的观点 | 现有原则禁止预设性格和编造，但没有明确区分有依据的观点与虚构经历 | 可试验更明确的参与方式指导 | 不能据此断言真实性要求必然导致疏离 |
| 结束话题与减少主动联系 | Affect 只识别一组完整匹配的明确反馈；Wake 有 pause、免打扰与频率控制；普通 chat 没有通用的模型选择静默协议 | 主动发送已有边界；自然语言覆盖有限 | 本轮不新增关系状态机，也不将模型说“不会打扰”视为配置已修改 |
| 无记忆、错误记忆 | Memory 保留 CONFIRMED/HYPOTHESIS、needs_review、证据与遗忘重放；历史已有角色 | 这些真实性机制应保留 | 不把所有主体误归因都归为角色未传递 |
| 多条长气泡 | `reply_segments.split_text` 无损切分同一回复，`Core.run_once` 只生成一次文本 | 气泡数不是交流主动性的指标 | 分段本身是否降低体验需要展示同一原文进行判断 |
| 用户提供的关系/身份样本 | 已保存 5 个连续主人 turn 与 11 个实际 SENT 片段；没有实际截图或历史完整模型 payload | 可作为可见对话重建基线 | 不能补写缺失段落、纳入未发送内容或声称复现历史完整请求 |

## 成熟实现与评测方法

[DSH system-prompt](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/system-prompt/README.md)
把静态指导与有来源的运行上下文分开组装；本实验采用这个区分，不引入新人格或状态系统。
已读源码 blob 为 `48b43666ee0180ea5b96bec80c915aaa429e97bc`。
[Pydantic Evals](https://pydantic.dev/docs/ai/evals/getting-started/core-concepts/) 使用显式 cases、
inputs 与 metadata 组织实验。这里采用可移植 JSON case 数据，并复用仓库现有离线
Core.context 实验方式；不为一个小实验新增运行框架。

[Chatbot Arena](https://arxiv.org/abs/2403.04132) 提供成对人类偏好评测的参考；
[MT-Bench 研究](https://arxiv.org/abs/2306.05685) 提醒位置、冗长和自我偏好会干扰评判。
因此两种策略在每个 case 中使用完全相同的历史/事实、模型名、输出上限及预算规则；
只改变交流指导，交错运行、隐藏策略标签、平衡左右位置。自动长度或问号统计只作描述，
不等于自然度评分；本轮不让模型自行宣称自己的改进有效。

## 第一轮实验及后续边界

36 个合成 case 覆盖日常分享、吐槽、兴趣、幽默、简短确认、话题切换、跨会话事实、
边界表达、无记忆、冲突记忆、已遗忘来源和主体归属。完整真实样本只保存在本地私有
目录，不上传仓库；已单独准备 3 对重复的 pilot，绝不冒充合成或真人盲评结果。

候选策略只调整如何参与当下对话，不提供固定回答、不预设名字、性格或关系身份。
基线保留现有原则；实验版保留真实性、权限与证据要求，尝试减少无必要的解释、建议和
反问，允许有理由的观察与不同意见。主人明确求助时仍应有用。

盲评分别记录自然度、交流意愿、刻意感和事实准确性，并支持持平/两者都差。
先按预先登记的标准评全部 case，再看失败类别，不能只挑喜欢的回复展示。
只有得到同条件的真实回复和盲评后，才能判断是否进入最小可开关实现阶段。

真实付费调用、VPS 部署、QQ 发送、生产配置更改和 PR 合并均需另行授权。
目前真实模型费用为零，没有体验提升结论。离线检查只验证实验准备与事实输入一致性。
