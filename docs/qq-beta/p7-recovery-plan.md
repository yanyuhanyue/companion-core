## 已核对范围

2026-10-20 重新通过既有 SSH 连接只读盘点。仍有 3 个容器、2 个运行，
17 个 bind 挂载条目、16 个不同来源。容器身份/镜像/状态/端口、挂载、启动时间、
restart count、网络、命名卷与监听均与 P6 相同。两个 redroid 容器共用同一个数据来源；
还原时只能选择一个运行，不能因恢复而同时启动二者。

已检查 21 个路径的权限与归属元数据，无 stat 错误。实际 bind 源目录、解析路径、
镜像 ID/引用/可用 RepoDigest、网络/重启/设备/权限参数及 1Panel systemd unit 位置
留在工作区私有恢复清单中。没有读取 Config.Env、启动参数、业务配置/数据库、日志正文、
QQ 会话或密钥。恢复时还需要由批准的加密备份保全这些必要的私密运行配置；元数据不能重建全部服务。

服务器可见一块约 80 GiB 磁盘。供应商控制台概要显示系统盘 80GB、数据盘“不需要”。
当前实例的概要、控制菜单、设置页均未发现快照管理入口；设置页仅显示 ISO/启动项。
控制台提醒用户自行做异地备份。**这不能证明供应商绝不支持快照**；该套餐的可用性、
一致性方式、费用、存储位置与恢复流程均待确认。官网通用的
[云服务器介绍](https://www.guanxingyun.com/cloud/index.html)不能代替实例能力证据。

## 首选：供应商整盘快照

由主人或经明确授权的操作者向供应商确认：当前套餐是否支持系统盘全部分区快照、
快照是否独立于实例删除、保存区域/保留期/计费、是否要求停机或暂停 I/O、
是否提供从快照新建隔离实例或挂载副本的恢复入口。
本轮未提交工单或联系他人。确认前不点救援、重装、重启、挂载 ISO 或购买升级。

具备明确选项后，提交一次具体审批：对象、盘范围、费用上限、保留期、影响窗口、
恢复责任人和独立校验目标。批准后才创建，保存成功 ID/完成时间/覆盖范围/位置回执。
优先在独立且禁止 QQ/公网业务出网的目标挂载副本；核对分区、必要文件及应用恢复，
不覆盖在线路径、不把克隆服务接回原流量。不能演练整机时如实保留残余风险，安装仍阻断。

## 备选：独立离机加密备份

可选目的地是主人本机 E 盘的工作区私有备份目录；只读检查时可用约 248.8GB，
未创建备份或密钥。也可选主人已有的独立存储。目标、密钥保管及恢复窗口未确定，
**不能据此开始读取/复制私人业务数据**。备份只保存在原 VPS 上不合格。

拟纳入的最小恢复集合：

| 对象 | 保全内容与一致性要求 |
|---|---|
| 1Panel | unit、二进制/版本、私密配置、站点与面板数据；在线数据库使用其受支持的一致性导出方式 |
| OpenResty | 当前挂载的配置、证书、站点数据及必要模块、镜像和网络配置；保留 uid/gid/mode/ACL/xattr |
| redroid | 私有清单中的真实 bind 数据目录及启动/设备/权限配置、当前与退出镜像；Android 运行中拷贝不能宣称应用一致 |
| Docker | 必需镜像导出或可验证的固定仓库摘要，容器启动及网络定义；秘密参数只能进加密档案 |
| 主机恢复入口 | 分区/文件系统、systemd、依赖版本与恢复凭据保管安排；SSH 私钥不纳入业务档案 |

执行前先确定每项一致性方法与预计数据量。若需要暂停 redroid/1Panel/OpenResty，
必须另行列出准确服务、停机上限及恢复步骤，请主人批准；不能把“保留服务”解释成停机许可。
不对运行中的 Docker 存储目录盲目 tar 后称为可恢复整机，也不把在线文件变化忽略为成功。
优先采用有校验的流式传输并在独立目标加密，避免 VPS 明文临时副本。
具体工具与命令须在目标/密钥方案确定后先做合成数据演练，再提交私人数据复制审批。

档案与解密密钥分开保管；主人持有离线恢复副本，不把密钥写入 Git、日志或与档案同包。
按主人对空间/流量的询问，额外只读统计了去重后的目录大小，未读取正文。
必要业务来源约 2.0GB、既有 Docker 镜像大小元数据约 4.7GB；文件级方案建议预留
10–15GB 档案、约 30GB 含本地验证空间、约 10GB 首次传输余量。镜像导出共享层、
压缩率与一致性方案会影响实值，这不是已生成档案的大小；整盘映像上限仍约 80GiB。
预计时间按实际选定字节数/限速估算，不虚构收费。
校验至少包括加密档案哈希/完整性、独立解密样本、权限还原以及隔离目标的应用恢复。
文件级备份若不能覆盖系统重建与 redroid 一致性，继续记录范围缺口，不能把 R1 改为 PASS。

## 非破坏性恢复顺序与失败处置

1. 主人指定恢复责任人和独立目标，先限制对外网络，保证克隆不会接管现有站点或 QQ。
2. 验证加密档案/快照与密钥，恢复到新盘/新目录，保留权限；不覆盖在线数据。
3. 校验 Docker/网络/镜像配置，再恢复 1Panel、OpenResty 的私密配置及站点。
4. 只启动选定的一个 redroid 副本，验证数据与服务状态；不自动恢复 QQ 登录出网。
5. 比较在线主机前后容器/监听/挂载摘要。发生意外差异立即停止扩大操作并报告。
6. 记录实际 ID、成功时间、范围、存储位置、保管方、恢复入口与校验结果。

失败时停止本轮备份/验证任务，保留错误证据与已有档案，由主人决定重试或清除。
不删除旧恢复点、不清理现有卷、不执行 `down -v`，也不自动回滚在线整盘。
未来 Core 的 DB/最新独立 ErasureLedger 备份另行验证，旧备份恢复必须先重放最新 Ledger。
