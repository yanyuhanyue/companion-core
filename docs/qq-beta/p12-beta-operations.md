# P12 私人 Beta 运营与后续常驻设计

这是 A–E 工程范围中的 E1–E4。当前仍使用独立有界窗口，最多五次模型尝试；
Memory review、Vision 和 chat 共用该总数。本文不启用常驻服务、连续续签或额外发送。
准确基线及已有真人证据见 [P12 基线](p12-baseline.md)。

## E1：先验边界与真实体验分开

| 轨道 | 进入真实窗口前 | 窗口内及自然日后 |
|---|---|---|
| 身份与投递 | 接收认证、主人/机器人/收件人、来源签名、幂等、重连、SENDING/UNKNOWN、停止及新旧窗口接续 | 手机实际收到多少条；重复检查有独立依据 |
| 费用与媒体 | 原预算预留、账户/本地限制区分、最终实际请求、图像 CDN/DNS/TLS/租约/大小及真实模型协议 | 各阶段实际 usage、缓存、估值、独立账单；确实看到图片的真人核对 |
| 隐私与恢复 | 最新 Ledger、并发遗忘、旧备份、原预算与 Window/Spool 恢复不增额 | 纠正、遗忘与来源覆盖的真实反馈 |
| 体验与成长 | 原生可撤销 SHADOW、日记来源和删除闭包、目标状态 | 自然度、漏忆/错忆、日记审阅、主动分享是否打扰；真实 3/7/14/30 日逐步观察 |

启动材料必须显式设 `proactive_enabled=false`。
[准备配置](p12-private-beta.example.toml) 显式关闭未批准模块，模型金额及探索请求额度为零；
它不含身份、密钥或运行许可。获准后由既有部署/窗口物化流程生成单独固定配置，
不能把该模板的存在或通用 Settings 默认值当成已部署配置。

## E3：私人反馈与汇总

后续 P13 对 `authorized_runtime` 增加了批准/trace/Inspector 关联要求，详见
[P13 运营说明](p13-beta-operations.md)。以下保留 P12 交付时的能力记录；缺少关联的历史
真人反馈需补齐真实材料后才能重新进入当前汇总器，原始历史文件不改写。

继续使用 `companion inspect-context --trace-id` 和 `status/observe`，以及原反馈验证器。
Inspector 增加原事件 UTC 时间、请求/逻辑请求哈希，仍只读 SQLite，仍为 `NOT_REVALIDATED` 诊断。
日期取原事件发生时间，不把检查报告的导出日期当成新一天聊天。
已遗忘事件不再导出发生时间；历史私有导出仍须按既有保留/删除规则管理。

[P12 反馈模板](p12-beta-feedback.template.json) 沿用 P11 schema，新增可选 coverage、记忆/日记/目标/分享体验，
以及手机可见回复数和重复检查依据。原 P11 记录继续有效。评分仍为 1–5，没观察到则 null；
多条可见回复必须同时记录重复事故，`SENT` 不能自动填手机已收到。

把反馈和对应 Inspector JSON 放入同一个私有目录，在
[汇总清单模板](p12-beta-observations.template.json) 的 `samples` 填相对路径：

```json
{"feedback":"first.feedback.json","inspector":"first.inspector.json"}
```

`feedback.inspector_sha256` 必须匹配 Inspector 文件的实际 SHA-256，trace 和候选也须吻合。
只有人工反馈而无 Inspector 时，`inspector` 与 `inspector_sha256` 都为 null。
清单自身不是批准或证据认证。

```powershell
.venv/Scripts/python.exe scripts/validate_beta_feedback.py .local/beta/first.feedback.json
.venv/Scripts/python.exe -m scripts.summarize_beta_feedback .local/beta/observations.json
```

汇总器仅打开清单明确指定的本地文件，最多 512 条、合计 16 MiB；不连接数据库、服务器或模型。
越出清单目录的路径、摘要/trace/候选不符、冲突的同事件反馈、重复模型请求或伪装为实际 Token 的
UNKNOWN 用量均拒绝。完全相同的重复记录只统计一次。错误输出不带文件名、正文或异常原文。

输出按 `NOT_RUN`、`local_synthetic`、`authorized_runtime` 自报类型分组，绝不合并为真实成绩：

- 输入认证与发送尝试仍需协议回执；只有 Inspector 的 Outbox 状态时，这两项为 null。
- 已记录模型调用、I/O fence、逻辑请求、input/output/cache-hit Token 分开。
  UNKNOWN/RESERVED 的 Token 不作实测；原账面金额与预留金额分别保留，不自动退款或结算。
- 同一账单依据只计一次；同一依据出现不同金额需先处理冲突。数值仍为自报账单，
  未证明账户、调用分摊或对账，`supplier_invoice_verified=false`。
- 只有同设备 UTC 或校准时间对及依据均齐全，才进入 E2E 样本；至少两对才给出 nearest-rank P50/P95，
  同时显示样本量。阶段时延与 Worker 活跃不填入手机 E2E 或持续健康时长。
- coverage 区分 ID、正文、卡片元数据、原图和分析；缺字段保持未观测。
  列出事件日期不证明连续在线或跨日质量，模拟日期也不晋级为真人天数。

汇总含私人关联的日期和统计，默认保存在 `.local/`；公开前重新做匿名汇总。
它没有删除副本或重新验证来源的权限。原材料在遗忘后失效时，应从清单移除或重新导出并按保留规则处理。

## E2：持久累计限额的后续合同

以下是未实现、未批准的设计，不改变本轮五次尝试限制。
当前应用金额限制不能约束同账户在其他程序中的调用，更不等于供应商账户硬封顶。
长期 Beta 的授权必须显式区分这些责任。

1. **身份与周期**：批准一个稳定、私有的 provider/account 归属引用，绑定币种、时区和起止时间。
   Key 轮换不能改变账户归属以取回额度。不能证明两个 Key 的关系时暂停，不合并或重置历史。
2. **现有账本扩展**：在原独立 Budget Journal 中追加版本化的周期范围/预留/停止记录，
   在原完整 Window Journal 中保留接收及发送计数，不另建钱包或把 SQLite 当独立责任副本。
   旧记录按已验证的 cutoff 引入；无法归属的 UNKNOWN/预留保持占用并阻断扩大。
3. **统一准入**：每次 reserve 同时检查窗口、自然日、自然月和账户范围金额/次数；
   接收、可见回复上界及 I/O 尝试分别计数。最紧的上限生效。
   先锁定及 fsync 原独立责任，再允许实际 I/O；跨账本中断保守占用，不能靠 DB 回滚重获次数。
4. **暂停与续签**：PAUSED/STOPPED 只禁止新动作，允许原责任结算和人工恢复检查。
   续签追加新的精确授权及边界，不清除累计计数、旧窗口、删除 Ledger 或未定责任。
   没有新批准时不循环建立小窗口。
5. **时间与恢复**：用 UTC 事件记录及批准时区划分自然周期；时钟倒退、周期归属冲突、
   独立日志缺失或序列漂移均暂停。恢复重放最新责任后核验所有维度，旧快照不能清零新周期负债。
6. **告警与保留控制面**：告警目标单独批准；告警失败不继续扩大业务。
   停业务后保留受鉴权的只读 status/observe、准确 STOP 和恢复检查入口，不用它们绕过窗口发信。

必须先通过双进程争抢、reserve/fsync/I/O 各中断点、共享 Key 漂移、跨午夜/月、
时钟倒退、迟到 usage、旧备份及发送不确定的反例，再考虑新的常驻批准。
没有这些证据时，现有有限窗口仍是实际可执行范围。

## E4：恢复补足与回滚

P10 已通过的应用集恢复不包含 QQ 登录卷、宿主原服务或整机。
[恢复申请模板](p12-recovery-request.template.json) 沿用
[R1/R2 对象合同](p10-r1-r2-signoff.md)，把每个对象的读取、停写、加密、离机、隔离恢复和验证单列。
当前各项均未批准，目标、大小、费用、时限、密钥持有人及回执必须获准后据实绑定。

准入顺序是：核对当前写者及最新 STOP → 固定非空一致性清单和三类独立记录 →
获准对象加密并独立保管密钥 → 新目标技术性禁止 QQ/模型/原服务出站 →
解密和原生兼容迁移 → 最新 Ledger 与预算/窗口责任回放 → integrity/FK/计数/不复活/不重发验证 →
准确停止回执。QQ 登录材料只验证隔离回读，不能自动登录或发送。

原服务与整机分别列入批准或明确未覆盖项。发生身份/权限漂移、账本断裂、遗忘复活、重复投递、
未知成本、错误收件人或原服务异常时，停止新增动作并保留不可变回执；回退不覆盖旧在线卷，
不恢复旧预算或窗口取得额度。独立新批准前保持 `private_beta_ready=false`。
