# P8-C.1 恢复与六项审批增量

本增量复用 [六项准入包](p8c-readiness.md) 与 [可填写记录](p8c-readiness.json)，不复制整份审批表。
证据等级 `OFFLINE_PROPOSAL`；恢复、部署、QQ、付费保持 BLOCKED，M1/Reader G1 保持 DISABLED。
本轮未连接主机、盘点私密文件、备份/复制数据、部署、停机、登录或发送 QQ，也未调用真实模型。

## 一致性集合：增量验收点

沿用现有 Core `backup/restore`，不创建第二套备份实现。先批准所有写入者清单与停止边界，再形成同一截止清单；
跨 DB/独立文件的一致性不是天然原子。尚未形成的真实值全部 null。

| 集合 | 需要实际记录与核对的内容 |
|---|---|
| Core | SQLite 一致快照含已提交 WAL；事件/Outbox/model_usage/admissions/windows、身份/归属和 schema。源 DB/WAL/SHM 状态纳入清单，活动单文件盲拷不能代替 backup API；SHM 不是单独恢复授权 |
| 最新 ErasureLedger | ledger_id、原生末 seq、文件/末记录 hash、截止时间、独立托管；恢复前验证身份/顺序并回放。它不是预算 journal 的 hash-chain 格式 |
| 最新 Budget Journal | 所有仍关联 admission 的历史/轮换 custody，journal_id、记录条数、末记录序位、链尾/file hash；没有原生 seq。对账 RESERVED/UNKNOWN、金额和 I/O fence，不能只保存当前启用配置指向的文件 |
| Window Journal + Spool + epoch | 每个窗口原生末 seq/链尾/file hash、Spool 一致快照、stable epoch、输入/发送 reservation、未确认项和实际剩余许可；不得通过旧副本/新 epoch 赠送额度 |
| SnowLuma 三卷 | 数据、登录、配置的实际卷引用、密文 hash/大小、权限/镜像与一致性停止批准；恢复副本技术性禁止 QQ 出站，不自动登录/扫码/发送 |
| 原服务/宿主 | 仅对获准范围分别列 1Panel/OpenResty/redroid、应用数据库、定义/权限与导出/停机办法；供应商整机快照覆盖、恢复入口、费用仍须本实例证据 |

独立路径不等于独立故障域；三类记录须证明可用的独立托管/密钥恢复及最新性。
DB 和所有独立副本一起回滚/丢失不能由本地 hash 排除，继续阻断，不能宣称有新额度。

停止顺序在准确批准范围内固定：停止新增输入与受控发送 → Bridge → Worker → API，以及其他获准写入者。
SnowLuma/原服务另批，不能因本项目维护就停止。对在途模型/发信保留 UNKNOWN 与全额上界；停止无法撤回 I/O。
关闭批准后仍可能到达更高费用/账单，应保全核账材料；最终停写前若出现结算/遗忘更新，重新取末位置并修订清单，不能丢弃晚到证据以制造“一致”。

新隔离目标必须与在线卷不同，默认禁止 QQ、模型、社交/站点业务出站，且有技术隔离验证；只关功能开关不足。
恢复的 Core 先在未发布临时库迁移到所固定镜像的 head、验证最新 Ledger、回放删除并检查 integrity/FK，再发布新文件。
Core restore 不会同时恢复 Budget/Window journal、Spool、QQ 卷或原服务；每项需独立验证/签收。

活动 Outbox 保留 `DELIVERY_UNCERTAIN`，SENT/CANCELLED 不退回待发；RESERVED 费用转 UNKNOWN 并保留金额。
有付费 admission 的恢复库保持 `model_budget_restore_required=1`，来源 grant/设备会话不恢复未来权限。
旧 COMPLETE 模糊归属继续 fail closed；纠正后继/派生资料依最新 Ledger 删除，合法独立事实保留。
未来 C1 的 runtime_meta 窗口/输入绑定也须列入恢复验收：不能清除绑定、审批或三账本来重开额度；
不得自动恢复 live 执行，必须在最终实现上验证旧库/独立账本/窗口配额的交叉恢复行为。

## 六项独立批准及执行依赖

| 请求 | 本增量的依赖与停止条件 |
|---|---|
| R1 恢复 | 精确源/全新目标、每项数据/停止/费用范围、密钥托管/RPO/RTO；得到真实非空集合与逐项对账证据。空库/合成通过不满足 |
| R2 部署 | R1 的获准真实隔离恢复、最终候选 SHA/三镜像 digest/配置与挂载网络 hash、0015→0016→0017 及兼容回退；默认 Demo/功能关闭 |
| R3 QQ | R2、新时窗/唯一 owner-bot/epoch/匿名白名单、输入≤5/外部尝试≤5/并发1/一次最多一条；真实认证事件来源、手机成对计时与停止人。staged JSON 不证明真实平台来源 |
| R4 付费 | [官方技术合同核查](p8c1-provider-contract-review.md) 与实际账户/费率/精确 framing/tokenizer/账户侧硬限额、唯一入口、独立预算 custody、核账和停止人；代码兼容不消除供应商阻断 |
| R5 M1 | 独立获准真实证据、确认/纠正/遗忘/旧备份回放；涉及费用/QQ 时分别满足 R4/R3。C1 首期 live-text 明确不启用 M1，与有界窗口联用需后续独立实现/审查 |
| R6 Reader G1 | 独立来源/账号/grant/期限/读取字节次数/撤销与遗忘；revoke 只停未来读取，另行 forget 才删除历史闭包。C1 首期不启用 Reader；不继承 M1/付费或设备权限 |

建议未来批准顺序：完成离线与供应商可行性核查 → R1 → R2 → 独立的 R3 Demo 窗口；
R4 可与 QQ 分开验收，联用时必须另有经审查的 live-text 有界入口、真实事件捕获和两项同时有效的准确批准。
M1/Reader 再分别验收，不跟随 live-text 首期一起打开。所有 QQ 指令的 `/` 合同由独立指令工作线验证；
普通 live-text 窗口不能借指令解释启用其他能力。

真实配对 E2E 仍 `n=0,p50/p95=null`，严格场景仍 0/5、0/20；ACK、stub、网络探针和旧目标手机样本均不能补齐。
费用/usage/cache/token/延迟没有真实样本时继续 null。六份记录单独绑定主体、操作者、时间、候选/摘要、范围、额度、停止人与回退。

## 停止与兼容回退增量

目标/授权/身份/epoch/配置或源码证明变化、账本不完整/不一致、意外业务出站、UNKNOWN 被清零或自动重发、
原服务异常时停止扩大动作。保存 DB/WAL、Spool、stable epoch、三类最新记录及配置/密钥版本引用；
不覆盖在线卷、不降级丢弃 0017 admissions、不清空新窗口绑定，不以旧镜像/旧账本获得新额度。
只有已证明兼容当前 schema、账本与 C1 绑定的固定镜像可申请恢复；没有兼容证据则保持停止，在全新隔离目标重审。
本文件只补准入与验收范围，不批准或执行其中任何实机步骤。

本增量的机器状态见 [contracts gates](p8c1-contracts-gates.json)。它只汇总 C2/C3 证据，
C1 的最终产品候选及兼容性仍待其他工作线冻结；离线兼容成功不能提升真实 provider、恢复或六项批准。
非作者已复核本增量与两种替代设计，结论仅限设计可审、运行继续阻断。具体验证由定向检查与交付提交记录。
