## 总览

| 机制 | MaiBot 实际情况 | Companion Core 现状 | 建议 |
|---|---|---|---|
| 对话参与决策 | 防抖、@/提及强制触发、群聊动态门槛和空闲退避，均已接线 | 每条主人消息立即生成回复，新消息到来时取消重做 | 私聊先做输入防抖；门槛和退避留给群聊 |
| 表达与黑话学习 | 从聊天原话学表达和黑话，AI 自审后入库，回复时注入 | 只学“简短一点”这类明确反馈，加上需审批的 B 站评论风格；没有黑话 | 学主人私聊里的黑话，只用来理解；不照搬全群学习 |
| A_Memorix 长期记忆 | 图谱、向量、Episode、人物画像，工程量大，检索质量没有真实评测 | 证据核验和擦除比它严格；缺时间属性、别名索引和召回解释 | 只借数据字段和规则，不换存储栈 |
| DSH / ACP Agent | 用 ACP（JSON-RPC over NDJSON）连接 DSH，拿到进度、取消、续接；权限自动批准 | 一次性 SDK 调用，只拿最终文本，撤回后进程停不下 | 执行器和 DSH 之间改用 ACP，权限请求回到主人审批 |
| 桌宠与内部聊天 | pywebview 子进程，所有通道汇入同一主人会话 | 入站契约写死 QQ | 做第二通道前先拆开“主人身份”和“QQ 号” |

## 1. 对话参与决策

**MaiBot 的做法**
- 每条消息进入调度流水线（`src/maisaka/turn_trigger/scheduler.py:64-105`），依次判断防抖、暂停、@/提及、空闲退避、动态门槛。
- 防抖“自然”档：安静时开批等 2 秒，活跃时 5 秒；同一人续发再等 2 秒；裸图至少 4 秒；整批最多 8 秒；@/提及最多 1 秒（`src/chat/debounce/controller.py:18-104`）。
- 群聊的回复概率是逻辑回归，最大权重是“近 5 分钟自己发言占比”（2.65），权重用他们自己的群聊日志拟合（`reply_likelihood.py:22-30`）。阈值按每小时目标回复数做反馈，只收紧不放宽（`dynamic_gate.py:163-211`）。私聊不走门槛和退避，只有防抖（`gates.py:75-77`）。
- wait/stop 是模型可调用的工具，每轮都是一次模型调用（`builtin_tool/wait.py`、`stop.py`）。

**Companion Core 现状**：每条主人消息直接建 chat job（`companion/core.py:262`）；新输入取消排队中和运行中的旧回复（`companion/reply_revision.py:100-135`），模型调用在途时要等它结束，所以连发几条时会白花一次调用。普通文本没有输入防抖，模型也不能选择不回复。

**建议**
1. **私聊输入防抖（优先）**：仿照戳一戳已有的合并窗口（`companion/poke_protocol.py`），给 chat job 加“最早认领时间”，取值参照自然档（2/5/2 秒，整批 8 秒）。不增加模型调用，还能减少取消重做。
2. 收尾、应答类消息（“嗯”“晚安”）允许模型显式输出“不回复”。这改变每条必回的约定，需要主人先认可。
3. 群聊以后再做：@/提及/名字别名强制触发、空闲退避、频率为 0 时静默维护历史、只收紧的反馈门槛。权重必须用本项目自己的数据重新拟合。
4. 不照搬：wait/stop 工具循环和流式打断。它们每轮都要调用模型，和本项目“一个 job 一次结算”的预算与 Outbox 模型冲突。

## 2. 表达与黑话学习

**MaiBot 的做法**
- 上下文裁切下来的用户原话进入学习，每批至少 10 条，间隔至少 30 秒（`src/maisaka/runtime.py:1840-1933`）；默认所有群聊和私聊都学（`src/common/utils/utils_config.py:30-31`）。
- 表达：一次模型抽取出“情境→说法”，代码过滤 bot 自己和黑名单用户，再对每条候选单独调用一次模型自审（`src/learners/expression_learner.py:406-737`）。只有完全相同才合并，没有衰减。回复时按出现次数加权抽样最多 10 条，不额外调用模型（`src/chat/replyer/maisaka_expression_selector.py:140-188`）。
- 黑话：只抽用户消息；数据库只存消息引用，推断时回查原文；出现次数达到 4、8、25、100 时推断含义，每次用三次调用：带上下文推断、只看词推断、对比两者，不一致才判为黑话（`src/learners/jargon_miner.py:32`、`:438-528`）。回复时作为“猜测含义，不一定为真”的参考注入（`src/maisaka/jargon_context_matcher.py`）。
- 管理只在 WebUI，没有聊天指令；学习主体的单元测试很少。

**Companion Core 现状**：`companion/growth.py` 只学主人明确反馈的两个维度；B 站评论风格走 `style_distill`，需要两个开关加主人审批才进回复；没有黑话学习，也不学主人自己的说话方式。

**建议**
1. **主人私聊黑话学习**：借用“只存消息引用 + 阈值推断 + 两次推断对比”。条目只用于理解主人，不用于模仿；释义标为猜测；条目接入擦除，来源消息被遗忘时一起删除。推断只在少数阈值（例如 4、25）触发，计入独立日预算。
2. 为表达候选补衰减：长期没用到的候选降权或过期。MaiBot 有字段但没实现。
3. 不照搬：默认全群学习并保存第三方原话；用 AI 自审代替主人审批。

## 3. A_Memorix 长期记忆

**MaiBot 的做法**
- 写入：每 36 条消息做一次摘要抽取；每条机器人回复额外调用一次模型写回人物事实，提示词要求引文但生产路径不核验（核验函数只在测试里调用，`src/services/person_fact_verifier.py`）。人物画像每 30 分钟刷新，每人一次模型分类。
- `fact_claims` 设计较好：区分权威性、稳定性、单值/多值；单值属性出现不同值时标为冲突；只有显式 supersedes 才让旧事实失效；证据撤空后变为 retracted（`src/A_memorix/core/storage/metadata_fact.py`）。
- 检索不调模型：双向量池、动态图权重、语义分低时启用 BM25、PPR 加分；后验图补位默认关闭。
- 遗忘：关系按 24 小时半衰期衰减，冻结后进回收站。删除是软删加快照，快照保留原文且从不清理，不是真正擦除。
- 约 781 个测试，基本都是机制测试，检索质量没有真实评测。

**Companion Core 现状**：引文必须是原文子串（`companion/memory.py:234`）；失去证据的记忆降为 HYPOTHESIS；冲突标 needs_review；27 个派生数据清理处理器保证擦除可回放。这些都比 A_Memorix 严格。缺口是：没有时间属性，不区分持久事实和事件；去重只比完全相同的内容；纠正一条记忆时清空全部摘要；召回没有得分解释；没有别名索引。

**建议（按价值/成本排序）**
1. 在 `REVIEW_RULES` 写明“持久事实 vs 带日期的事件”“不同日期的同类事件各自保留”，增加 possible_duplicate 并归入 needs_review。不增加调用。
2. 记忆加 stability、cardinality、valid_from/valid_to，从原事件派生，随证据链擦除。
3. 纠正时只作废证据重叠的摘要和 episode，不再全部清空。
4. 控制台显示召回解释：词法/语义名次、融合分、证据编号。纯本地计算。
5. 从已确认记忆提取名字，建可重建的别名索引并注册擦除；不引入图数据库。
6. 用真实标注样例做检索评测护栏（P@1、MRR 和下降阈值），不用自动生成的查询。
7. 不照搬：Faiss + scipy + 29 版 schema 的存储栈；每条回复抽取一次且不核验引文；24 小时自动衰减删除；可恢复快照和回收站（与擦除冲突）；每 30 分钟用模型做画像分类。

## 4. DSH / ACP Agent 接入

**MaiBot 的做法**
- 外部 agent 通过 ACP v1 连接，JSON-RPC 2.0 承载在 NDJSON 上；DSH 以 `dsh --profile acp` 子进程运行（`src/agent/acp.py:59-139`）。客户端声明不提供文件和终端能力。
- 流程：initialize → session/new 或 resume → session/prompt；进度通过 session/update 流式返回；取消发 session/cancel，宽限期过后杀进程组（`src/agent/acp_agent.py`）。在途任务重启后记为结果未知，不重放。
- 权限：外部 agent 申请权限时自动选 allow_once（`src/agent/acp.py:209-213`）；外部进程不隔离，继承完整环境变量，还能读任意聊天历史。整个功能标为实验性。

**Companion Core 现状**：审批链完整（来源校验、scope 摘要、一小时过期、预算代理、独立 UID、不重放）。缺口是：只有单轮调用（`companion/dsh_job.py`），只拿最终文本；主人撤回时执行器没有取消端点，进程停不下来；DSH 不能中途请求授权。

**建议**（属于新外部集成，按 AGENTS.md 需先和主人讨论范围；M0/M1 阶段只做设计）
1. 执行器内部改用 ACP 和 DSH 通信，Core 与执行器之间的 HTTP 信封、审批和回执不变。
2. 文件和终端能力声明为不提供；会话中途不扩大能力。
3. 权限请求回到 Core，按 scope 走主人审批，超时视为取消。
4. 主人撤回映射为 session/cancel，宽限期过后杀进程组，任务记为 UNKNOWN。
5. 不照搬：自动授权、外部进程不隔离、跨会话读历史、沙箱默认联网和任意 shell。

## 5. 桌宠与内部聊天

**MaiBot 的做法**：桌宠是 Windows 上的 pywebview 子进程，和主程序用 stdio 逐行 JSON 通信（`src/desktop_pet/service.py`、`pet_window.py`）。图文附件先写磁盘，管道只传请求编号，主程序严格校验大小和像素后立即删除（`attachments.py`）。所有消息以固定身份 internal/owner 进入和 QQ 相同的处理入口；代转消息一律不给受保护命令权限（`src/core/local_operator.py`）。消息没有幂等键，投递尽力而为。

**Companion Core 现状**：入站契约写死 QQ：`InboundEvent.source` 只允许 `qq.onebot`（`companion/contracts.py:64`），主人身份就是 QQ 号，授权链只认 OneBot 连接。

**建议**：做第二个聊天通道（网页或桌面）之前，先把“主人主体”和“通道”拆开；新通道复用控制台的 Cookie + CSRF 会话，客户端生成幂等键，新增投递通道并以客户端确认作为送达。可以借鉴附件磁盘交接、多端共用同一主人会话、代转消息不给权限；不照搬无幂等、无送达回执的投递方式。

## 建议的推进顺序

结合 2026-10-30 主人确认要解决的事项：

| 顺序 | 事项 | 理由 |
|---|---|---|
| 1 | 重签付费审批的输出上限 | 主人已同意；thinking 和正文现在共用 768 token |
| 2 | 私聊输入防抖 | 不增加调用，直接改善连发时的体验和费用 |
| 3 | 配置热加载（无停机计划第 4 阶段） | 控制台每次保存都要重启 |
| 4 | 模型服务商切换不改代码 | 续期机制写死了服务商、模型和密钥 |
| 5 | 控制台补审批操作 | 生活建议、QQ 空间计划、语音任务等目前只能看 |
| 6 | 记忆规则与字段（第 3 节建议 1–4） | 先改规则和字段，不动存储 |
| 7 | 主人私聊黑话学习 | 需要新预算场景和擦除接入 |
| 8 | ACP 执行器、第二聊天通道 | 新外部集成和契约变更，需先讨论设计 |
